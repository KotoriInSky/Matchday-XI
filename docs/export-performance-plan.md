# 基于开源方案的导出性能提升计划

日期：2026-10-19。依据 `ROADMAP.local.md` 中的分层渲染、视频导出和内存 TODO，以及当前工作区源码制定。

实施更新：当前优先优化静态网站中的浏览器导出；已减少不可见图层的捕获工作，并直接接入 Mediabunny 的背景视频时间采样接口，记录见[浏览器导出性能记录](browser-export-performance.md)。已检查 WebAV 的 Combinator／ImgClip 及 DOM 工具源码；整体合成迁移、Motion Canvas 原型仍待后续评估。本地 4K 已改用 FFmpeg 标准 RGBA 帧流；低分辨率对照没有稳定收益，继续保留 PNG 路径，见[本地导出性能记录](local-export-performance.md)。

## 目标与范围

优先提升浏览器及本地服务的视频导出吞吐，降低长视频和高分辨率导出的峰值内存。保留两套动画模板、现有素材与项目格式，保证字体、透明立绘、光效、裁剪、标签和背景视频的画面与时间轴一致。

首轮交付是可复现的基线、一个分层渲染原型及对照报告。根据实测决定迁移范围；自由人数、完整 ZIP 备份和自动抠图继续作为独立功能处理。

## 当前实现与待验证问题

| 环节 | 当前实现 | 下一步要回答的问题 |
| --- | --- | --- |
| 时间轴与布局 | `src/engine/stage.ts` 统一驱动动画；`src/render-export.ts` 按输出时间采样 | 如何复用同一套时间与布局数据，避免新渲染器产生第二套动画逻辑？ |
| 浏览器画面生成 | `src/lib/browser-capture.ts` 逐帧读取样式、克隆 DOM、嵌入素材、序列化 SVG，再解码绘入 Canvas | 样式计算、序列化和 SVG 解码各占多少？静态图层复用能省下多少？ |
| 背景视频 | 每帧等待视频 seek，视频帧转 PNG data URL 后嵌入 SVG | 顺序解码与直接合成是否能减少跳转和图片转换？ |
| 浏览器编码及输出 | Mediabunny／WebCodecs、有背压的逐帧提交、分块 MP4、OPFS 优先及内存回退 | 编码和写盘是否已成为瓶颈？Worker 能改善吞吐还是仅改善界面响应？ |
| 本地视频输出 | 2160p 从复用 Canvas 经 RGBA 二进制流直接送入 FFmpeg；较低分辨率保留 PNG／base64；每 120 帧重建渲染页 | SVG 生成和解码能否进一步复用？1080p／1440p 是否值得改用原始帧？ |
| 本地编码器 | 当前工作区已有 NVENC 实际探测和 `libx264` 回退选择 | 探测成功与完整导出稳定性是否一致？编码中途失败如何恢复？ |

Canvas 复用、统一校时、减少样式读取、增量 ZIP、背景视频二进制上传和 MP4 流式输出已有实现，作为后续方案的基础。

工作区已有未提交的本地帧捕获与编码器改动。建立基线时须记录 Git 提交、工作区补丁和新增文件的摘要，避免只用 HEAD 描述当前版本。旧的 720p／18 帧数据只作历史参考，不能代表当前完整视频导出性能。

## 开源项目的分工

实施原则：优先直接使用开源项目的公开接口、素材组件和现成算法；本项目只补必要的格式、CSS 和任务生命周期适配。解码、帧选取、缓冲池、编码和封装交给已有库；确实无法直接替代的部分再做小范围实现及对照验证。

以下项目来自现有 TODO。当前已核对 Mediabunny 1.61.4 的 CanvasSink、VideoSampleSink、CanvasSource 和 Input.dispose，以及 WebAV 提交 `42dd6fd65ccbda39c729265c14aab56ac4d28235` 的合成与素材模块；其他项目仍是后续候选。具体采用的接口与回退条件见实施记录。

| 项目 | 研究或复用内容 | 本项目的落地点 |
| --- | --- | --- |
| [WebAV](https://github.com/WebAV-Tech/WebAV) | 素材生命周期、图层合成、按时间取帧及流式处理 | 验证背景、卡框、立绘、文字、标签与光效分层；比较直接使用其组件与自行实现小型合成器的成本 |
| [Motion Canvas](https://github.com/motion-canvas/motion-canvas) | 场景结构、确定性时间采样、布局与渲染组织 | 借鉴共用场景描述和时间轴的方式，先验证一张卡片与一个转场；不预设迁入整套运行时 |
| [Mediabunny](https://github.com/Vanilagy/mediabunny) | 现有编码、封装、背压与输出能力；核实当前版本的解码／取帧 API | 保留编码出口，评估背景视频顺序解码、VideoFrame／ImageBitmap 传递和 Worker 分工 |
| [Remotion](https://github.com/remotion-dev/remotion) | React／HTML 视频渲染和隔离渲染实例的组织方式 | 用作本地 Chromium 管线的补充参考；采用前核对其自定义许可与商业条件 |
| [ffmpeg.wasm](https://github.com/ffmpegwasm/ffmpeg.wasm) | 格式兼容与缺少 WebCodecs 时的回退 | 留到兼容性阶段验证，分别核对包装层、FFmpeg 核心与编解码器许可，并测量下载、内存和速度 |

优先验证 WebAV 的合成方式，借鉴 Motion Canvas 的场景组织，保留 Mediabunny 的编码出口。是否新增依赖，由原型的性能、画面表现、包体和维护成本共同决定。

## 阶段 0：建立可信的性能基线

1. 固定项目素材、随机种子、字体、输出规格和关键采样时间；记录操作系统、CPU／GPU、浏览器、驱动、FFmpeg 版本及编码参数。正式性能对照使用相同的生产构建和启动方式，开发服务器仅用于调试；区分模块编译、素材下载和实际渲染耗时。
2. 从 `tests/export-resources.mjs` 扩展分段计时：初始化、校时／布局、样式读取、DOM 克隆、素材处理、SVG 序列化、图片解码、Canvas 绘制、编码提交及背压等待、封装与写盘。本地额外记录 PNG 转换、base64／传输、FFmpeg 解码及页面重建。
3. 使用完整导出测总用时和有效 fps；阶段耗时允许存在流水线重叠，不能简单相加，也不能把 `source.add()` 的等待全部当作编码器处理时间。读取 FFmpeg 进程完成时间，浏览器侧报告可观测的提交、等待与 finalize 时间。
4. 固定每个场景至少 1 次冷启动记录与 5 次预热后测量，分别报告完整导出用时中位数、范围，以及逐帧生成耗时的 P50／P95。性能采样与逐像素读回检查分开运行，避免读回改变 Canvas 后端或干扰计时。
5. 记录 JS 堆、ArrayBuffer／Blob、浏览器与 GPU 进程、Node 和 FFmpeg 的内存曲线；GPU 显存单列，说明共享内存与进程汇总的限制。无法可靠观测的项标记未知。

基准场景先覆盖两套模板各一个代表项目：透明立绘、中文／自定义字体、光效和关键转场。再分别增加图片背景及循环视频背景。日常比较以 720p／30 和 1080p／30 为主；候选方案通过后补 1080p／60、4K／30、4K／60，能力不足的规格记录原因。

产出：基准素材清单、机器可读结果和瓶颈排序。以新增的 `scripts/benchmark-export-pipeline.mjs` 为建议入口，结果写入已忽略的 `test-results/export-pipeline/`；当前阶段只计划这些文件。

## 阶段 1：验证最小分层渲染原型

选取一张包含中文姓名、透明立绘、标签和光效的卡片，以及一段具有缩放、位移和显隐变化的转场。

1. 明确静态内容、动态内容与合成边界。卡框、固定文字等只在内容不变时缓存；人物、标签与光效按效果拆层。涉及遮罩、混合、滤镜或 3D 变换的子树，先验证能否拆分，必要时整体捕获。
2. 比较两个小原型：A 复用现有 HTML／CSS，只缓存确认静态的子树并在 Canvas 合成；B 借鉴 WebAV，以独立素材与图层直接合成。用相同输入比较冷启动、缓存构建、逐帧生成、完整导出和内存，测量额外包体及接入复杂度。
3. 借鉴 Motion Canvas，定义最小场景描述和 `sample(time)` 输出的图层状态。复用现有 Stage 的布局、时间点、缓动和动画参数；迁移轨道时让预览与导出共用数据。原型阶段允许 Stage 提供采样值，避免先重写整条时间轴。
4. 先接入现有 `captureInto(canvas)` 出口和 Mediabunny，单独比较画面生成收益。后台保留现有完整捕获路径，按模板／效果能力选择实现。
5. 缓存键覆盖素材版本、文字、字体加载状态、语言、构图、颜色、模板和输出尺寸。项目切换、素材替换、取消与任务结束时清理；同时限制缓存项数量和估算字节数。

产出：同一输入可切换的原型、关键帧差异图、性能与内存对照，以及“采用 A／采用 B／暂停迁移”的结论。复杂 Highlight 的透视、遮罩和前后层级单独验证，不能用简单平移卡片的结果推断全部效果可迁移。

## 阶段 2：优化背景视频与流式管线

此阶段在原型通过后开展；若阶段 0 表明背景视频占主要耗时，可提前做独立验证。

1. 核实 Mediabunny 当前安装版本是否提供所需解码与时间采样能力，再决定复用方式。按解码顺序读取，依据源帧时间区间选择覆盖输出时刻的画面；覆盖 24／25／30／60 fps 和可变帧率素材。
2. 直接把解码帧绘入合适的合成层，验证替代“视频 seek → PNG data URL → SVG”的路径。保持原有裁剪、滤镜、透明度、遮罩和混合关系，并覆盖循环边界、首尾帧及关键帧后的跳转。
3. 初始解码预取限制为当前帧加至多 2 个后续帧，并另设字节预算；与在途编码帧、图层缓存合并核算。4K 下按帧尺寸估算占用并收紧队列，消费结束即关闭 VideoFrame／ImageBitmap。
4. 沿用按需生产、有界队列、编码背压和分块写盘。测量 10／30／60／120 秒导出的占用随时长变化；OPFS 路径与内存回退分别报告，保留下载结果的占用单独列出。
5. 如主线程阻塞明显，再评估 OffscreenCanvas／Worker 编码或合成；DOM 样式读取留在文档环境。分别报告吞吐与界面响应改善。

产出：视频选帧与循环正确性结果、长时内存曲线和流式管线对照。OPFS 不可用时，最终成品仍可能驻留内存，不据此承诺全链路固定内存。

## 阶段 3：优化本地传输与编码

1. 基于当前复用 Canvas 的确定性画面，比较 PNG 管线与可行的二进制／原始像素传输原型。必须把浏览器到 Node 的复制、FFmpeg 输入解码和背压等待全部计入，不能只测去掉 PNG 后的浏览器时间。
2. 原始 RGBA 一帧 4K 约 31.6 MiB，60 fps 约需 1.85 GiB/s 的未压缩数据吞吐；只有端到端测量证明有收益且内存可控时才采用。保留透明合成和色彩转换检查。
3. 测量每 120 帧重建页面的初始化成本，以及原生图片／SVG 资源占用。只在长时导出证明资源稳定后调整重建策略，测试重建前后连续帧的时间与画面一致性。
4. 先验证已有 NVENC／`libx264` 选择，再按可用硬件补 QSV、AMF、VideoToolbox 或 VAAPI。记录真实任务使用的编码器；用相近解码后画质比较时间与文件大小，不能直接把不同编码器的同名质量参数视为等价。
5. 编码中途失败的回退作为独立状态处理：关闭旧进程、清理未完成输出，再以 CPU 编码器从零重试。取消保持有效，进度与 ETA 随重试重置，并保留诊断原因。

产出：本地管线对照、已实测的硬件／系统矩阵和回退结果。当前 NVENC 探测与起始选择，尚不能证明所有硬件或编码中途恢复已覆盖。

## 阶段 4：按模板迁移并验收

先迁移原型覆盖的卡片和转场，再扩展 classic 的其他场景、season2627 和复杂 Highlight。每次迁移一个边界清晰的单元，保留完整捕获回退，记录走了哪条渲染路径。多实例分段渲染留到单实例瓶颈解决之后，再按 CPU、内存与 GPU 实测能力决定是否值得引入。

首轮采用以下候选门槛；它们是实施决策标准，不是已取得的提速或保证：

- 原型逐帧生成耗时中位数相对基线降低至少 30%，并检查 P95；代表性完整导出用时降低至少 20%。若只改善界面响应，单独报告，不记作导出吞吐提升。
- 720p 与 1080p 均测得收益；高分辨率路径不得出现崩溃或持续增长的资源保留。比较峰值内存及任务结束后的稳定占用，缓存增加的内存必须解释并受预算约束。
- 同一捕获实现的固定时间点继续保持像素一致。跨渲染实现不能只用哈希判定：先统计改变像素、最大通道差和透明边缘差异，再检查差异图；可接受的抗锯齿容差需按基准样本说明，布局、层级、光效与动画时点偏差必须修复。
- 按 `ceil(duration × fps)` 校验帧数，输出时长与预期误差不超过一帧；核对时间戳顺序、帧率及背景视频循环。针对关键转场和页面重建边界检查连续帧，防止闪烁、异常重复或丢帧。
- 连续完成、取消、失败后重试，确认队列、解码器、Worker、Canvas、对象 URL、iframe 与临时文件释放；历史下载结果按既有生命周期处理。
- 测量失败时保留现有默认路径和完整结果，停止扩大迁移，依据报告选择其他瓶颈继续优化。

验证复用现有 `test:export-resources`、`test:export-styles`、`test:export-frames`、`test:card-compositing`、`test:render-consistency`、`test:browser-export`、`test:export-media`、`test:export-storage` 与 `test:video-encoder`。按实际改动选择相关检查，加入原型专属差异和选帧验证；迁移进入默认路径前执行类型检查、构建及静态部署导出验证。

## 首轮实施顺序与交付

1. **基线与上游核实**：完成阶段 0，查明 WebAV／Motion Canvas 的具体模块和 Mediabunny 所需 API，固定候选版本及许可记录。
2. **最小原型**：完成阶段 1，只覆盖一张卡片与一个关键转场，输出两个方案与现有实现的对照。
3. **迁移决策报告**：列出逐帧和完整导出收益、内存代价、视觉差异、未支持效果及下一批可迁移场景；符合门槛后推进阶段 2～4。

首轮结束即可判断分层渲染是否值得继续。具体工期在基线与原型结果明确后估算，避免把上游项目的性能数据直接套用到本项目。
